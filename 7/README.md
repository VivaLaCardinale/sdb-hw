### Задание 1. Резервное копирование

*Кейс*
*Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. Необходимо описать, какие варианты резервного копирования подходят в случаях:*
*1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.*
*1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.*
*1.3.* * *Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.*
*Приведите ответ в свободной форме.*


### Решение 1.

1.1. Восстановление данных за предыдущий день
Для этой задачи подходит полное резервное копирование (Full Backup), т.е. создание копии всей базы данных целиком. Для этого нужно настроить ежедневное создание полного бэкапа (в часы минимальной нагрузки, например, ночью). Это будет гарантировать наличие «слепка» всех данных на начало текущего рабочего дня.
Плюсы: простота восстановления, полная независимость копии.
Минусы: требует много места и времени на создание.

1.2. Восстановление данных за час до поломки
В этом кейсе оптимально использовать инкрементальное копирование или бэкап логов транзакций (Transaction Log Backup). Т.е. сохранение только тех изменений, которые произошли с момента последнего бэкапа. Для этого нужно настроить копирование логов транзакций \ новых записей в БД каждые 50–60 минут. При сбое нужно восстановить последний полный бэкап, а затем «накатить» последовательность логов \ записей в БД до нужного момента времени. Важно что в данном кейсе все равно используется и полное резервное копирование.
Плюсы: минимальная потеря данных (RPO < 1 часа), экономия места.
Минусы: сложный процесс восстановления (нужна вся цепочка логов\данных).

1.3. Моментальное переключение на работающую базу
Да, такой кейс возможен при использовании репликации, т.е. данные в реальном времени копируются с основной базы (Master) на резервную (Slave/Replica). Важно что реплика это не резервная копия, т.е. все равно важно и нужно использовать полное резервное копирование БД.
Плюсы: нулевой или минимальный простой бизнеса.
Минусы: высокая стоимость.

### Задание 2. PostgreSQL

*2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).*
*2.2.* * *Возможно ли автоматизировать этот процесс? Если да, то как?*
*Приведите ответ в свободной форме.*

### Решение 2.

Для работы с PostgreSQL основными инструментами являются pg_dump для создания копий и pg_restore для их восстановления.

2.1. Команды резервирования и восстановления
Согласно официальной документации, рекомендуется использовать «кастомный» формат сжатия (-Fc), так как он позволяет восстанавливать данные в несколько потоков.

Резервное копирование (pg_dump):
`pg_dump -h localhost -U username -Fc -f db_backup.dump name_database`
где:
* `-h localhost`: хост, на котором запущена БД;
* `-U username`: имя пользователя;
* `-Fc`: формат "custom". Это самый гибкий формат: он сжат и позволяет выбирать конкретные таблицы при восстановлении;
* `-f db_backup.dump`: имя выходного файла;
* `name_database`: имя базы данных;

Восстановление (pg_restore):
`pg_restore -h localhost -U username -d name_database_new -j 4 db_backup.dump`
где:
* `-d name_database_new`: целевая база данных (куда восстанавливаем);
* `-j 4`: количество параллельных потоков (ускоряет процесс в 4 раза на 4-ядерном процессоре);
* `db_backup.dump`: файл бэкапа;

2.2. Автоматизация процесса
Автоматизация может быть:
* На уровне ОС (Cron / Task Scheduler). Самый простой и надежный способ — использование планировщика задач Cron в Linux. Т.е. создается bash-скрипт, который запускает pg_dump с добавлением даты в название файла.
* С использованием специализированного ПО. Например: `Barman` (Backup and Recovery Manager)  для PostgreSQL; `pgBackRest`, который считается быстрым и эффективным инструментом для очень больших баз, плюс поддерживает инкрементальное копирование и сжатие; `Veeam Backup & Replication`, если базы работают в виртуальной среде (VMware/Hyper-V) и т.д.
*  Docker и Kubernetes. Если компания использует контейнеры, то бэкап можно автоматизировать через Sidecar-контейнеры или CronJob внутри кластера, которые отправляют дампы в объектное хранилище (например, S3).

Важно помнить что автоматизация должна включать не только создание бэкапа, но и регулярную проверку его целостности.

### Задание 3. MySQL

*3.1. С помощью официальной документации приведите пример команды инкрементного резервного копирования базы данных MySQL.*
*3.2.* * *В каких случаях использование реплики будет давать преимущество по сравнению с обычным резервным копированием?*
*Приведите ответ в свободной форме.*

### Решение 3.

Для реализации инкрементального копирования в MySQL используются механизмы бинарных логов (Binary Logs). Именно они позволяют фиксировать изменения данных «на лету».

3.1. Инкрементное резервное копирование в MySQL
В MySQL инкрементальное копирование штатными средствами чаще всего реализуется через утилиту mysqlbinlog (копирование логов транзакций) или с помощью Percona XtraBackup (профессиональный стандарт для физических бэкапов).

Пример через Binary Logs:
Сначала необходимо убедиться, что в `my.cnf` включено логирование:
```
ini
[mysqld]
log-bin=mysql-bin
```
Для создания «точки отсчета» (инкремента) после полного дампа, нужно сбросить логи:
```
bash
mysqladmin -u root -p flush-logs
```
Чтобы сделать копию всех изменений, произошедших после последнего полного бэкапа, используется команда:
```
bash
mysqlbinlog /var/lib/mysql/mysql-bin.000001 /var/lib/mysql/mysql-bin.000002 > incremental_backup.sql
```
где:
* `mysqlbinlog`: утилита, переводящая бинарный формат в читаемый SQL;
* `mysql-bin.000001`: файлы логов, содержащие транзакции за конкретный период.


Пример через Percona XtraBackup (физический инкремент):
```
bash
#Создание инкремента на основе последнего полного бэкапа
xtrabackup --backup --target-dir=/data/backups/inc1 \
           --incremental-basedir=/data/backups/full_backup
```

3.2. Преимущества репликации перед обычным бэкапом.

Важно помнить что реплика не заменяет бэкап. Из плюсов использования реплики млжно выделить:
* минимизация времени простоя (RTO — Recovery Time Objective);
* масштабирование производительности (Read Scaling);
* бэкап без остановки системы (Zero Impact), т.е. снятие бэкапа с реплики;
* защита от физических катастроф, если реплика находится в другом дата-центре.
