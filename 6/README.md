# Домашнее задание к занятию "`Репликация и масштабирование. Часть 2`" - `Минаевой Екатерины`

### Задание 1.

Опишите основные преимущества использования масштабирования методами:/
1.1. Активный master-сервер и пассивный репликационный slave-сервер;/
1.2. master-сервер и несколько slave-серверов;/
Дайте ответ в свободной форме./

### Решение 1.

Эти две стратегии масштабирования и обеспечения отказоустойчивости решают разные бизнес-задачи. Если первая (Active-Passive) направлена в первую очередь на надежность (HA — High Availability), то вторая (Master-Slaves) направлена на производительность./
/
1.1. Активный Master и пассивный Slave (Failover Cluster)./
В этой схеме Master принимает всю нагрузку (чтение и запись), а Slave находится в режиме «горячего ожидания» (Hot Standby). Он не обслуживает клиентов, пока жив основной сервер./
Основные преимущества:
* Максимальная консистентность (целостность) данных. Исключены ситуации, когда пользователь записал данные, а при чтении (с другого сервера) их еще не увидел.
* Мгновенное восстановление (RTO). Пассивный сервер держит копию данных в актуальном состоянии. Т.е. в случае аварии на Master, переключение происходит очень быстро.
* Простота администрирования. Не нужно настраивать логику разделения запросов в коде приложения (Read/Write splitting). Приложение всегда «стучится» по одному адресу.
* Изоляция обновлений и бэкапов. Пассивный сервер — идеальное место для снятия тяжелых бэкапов или выполнения аналитических выгрузок не мешая при этом пользователям./

1.2. Master и несколько Slave-серверов (Read Scaling)./
В данном случае Master принимает только записи (INSERT/UPDATE), а чтение (SELECT) распределяется между несколькими Slave-серверами. Основные преимущества:
* Горизонтальное масштабирование чтения.
* Снижение нагрузки на Master.
* Географическое распределение.
* Повышенная выживаемость данных.

### Задание 2.

Разработайте план для выполнения горизонтального и вертикального шаринга базы данных. База данных состоит из трёх таблиц:
* пользователи,
* книги,
* магазины (столбцы произвольно)./
Опишите принципы построения системы и их разграничение или разбивку между базами данных./
Пришлите блоксхему, где и что будет располагаться. Опишите, в каких режимах будут работать сервера./

### Решение 2.

2.1. Принципы построения и разбивки./
* Вертикальное разделение./
На первом этапе нужно разделить базу на функциональные блоки, что позволит изолировать нагрузку разных модулей друг от друга./
`DB_Users`: Содержит таблицу `Users` (id, имя, email, пароль)./
`DB_Catalog`: Содержит таблицу `Books` (id, название, автор, цена, ISBN)./
`DB_Shops`: Содержит таблицу `Shops` (id, название, адрес, город)./
* Горизонтальное разделение./
Нужно применить его к самой быстрорастущей таблице `Users` и разделить её на сегменты (шарды) по ключу user_id.
`Shard 1`: Пользователи с ID от 1 до 5 000 000./
`Shard 2`: Пользователи с ID от 5 000 001 до 10 000 000./
/
2.2. Блок-схема архитектуры/
```
mermaid
graph TD
    App[Application Layer / API] --> Router{Database Router / Middleware}

    subgraph "Вертикальный шард: Users (Горизонтальное масштабирование)"
        Router --> Master_U1[(Master Users Shard 1)]
        Master_U1 --- Slave_U1[(Slave Users Shard 1)]
        Router --> Master_U2[(Master Users Shard 2)]
        Master_U2 --- Slave_U2[(Slave Users Shard 2)]
    end

    subgraph "Вертикальный шард: Books"
        Router --> Master_B[(Master Books)]
        Master_B --- Slave_B1[(Slave Books 1)]
        Master_B --- Slave_B2[(Slave Books 2)]
    end

    subgraph "Вертикальный шард: Shops"
        Router --> Master_S[(Master Shops)]
        Master_S --- Slave_S[(Slave Shops)]
    end

    style Master_U1 fill:#f96,stroke:#333
    style Master_U2 fill:#f96,stroke:#333
    style Master_B fill:#f96,stroke:#333
    style Master_S fill:#f96,stroke:#333
```

2.3. Описание режимов работы серверов./
В данной схеме реализован гибридный подход:
* Для таблицы Users (высокая нагрузка):/
Режим: Sharded Master-Slave./
Зачем: Таблица разбита на два физических мастера (горизонтальный шардинг). Каждый мастер имеет своего Slave./
Логика: Записи о новых пользователях распределяются роутером между шардами, чтение идет со Slaves./
* Для таблицы Books (много чтений, мало записей):/
Режим: Master и несколько Slaves./
Зачем: Книг много, их ищут тысячи людей одновременно./
Логика: Обновление каталога (поступление книг) идет на Master. Все поисковые запросы распределяются между двумя (или более) Slaves для обеспечения высокой скорости поиска./
* Для таблицы Shops (Низкая нагрузка):/
Режим: Active Master - Passive Slave./
Зачем: Список магазинов меняется редко и занимает мало места./
Логика: Slave нужен только для обеспечения отказоустойчивости (HA). Если Master упадет, Slave станет основным./
/
Что можно выделить:
* Проблему JOIN-ов. При вертикальном шардинге нелвозможно выполнить SQL-запрос JOIN между таблицами Users и Shops на уровне базы данных, так как они физически на разных серверах. Объединение данных происходит на уровне программного кода.
* Database Router. Необходим слой (например, ProxySQL или встроенная логика в backend), который будет знать: на какой сервер отправить запрос INSERT в таблицу Books, а также в какой шард пойти за данными пользователя с конкретным ID.
* Выбор ключа шардирования (Shard Key). Для таблицы Users выбран user_id. Это обеспечивает равномерное распределение. Если бы был выбран «Город», то один шард (например, «Москва») был бы перегружен, а другой («Магадан») пустовал бы.
* Масштабируемость. Эта схема позволяет масштабировать каждый компонент независимо. Т.е. если завтра книг станет в 100 раз больше, то можно добавить шардинг для Books, не трогая серверы с Users.
